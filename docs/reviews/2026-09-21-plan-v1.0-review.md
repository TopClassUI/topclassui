## Part 1 — Git line endings (answered)

**Do you need to do anything now?** No. The warning means: the file in your working tree is LF; because `core.autocrlf=true`, Git stored it as LF (correct) and would hand you CRLF on the next checkout. The commit is fine and the repo is LF-only.

**Permanent fix** — make LF the repository's enforced convention so it does not depend on any machine's Git settings (Linux CI, contributors and Prettier all expect LF):

1. Add `.gitattributes` at the repo root:
   ```
   * text=auto eol=lf
   *.svg text eol=lf
   *.bat text eol=crlf
   *.cmd text eol=crlf
   *.png binary
   *.jpg binary
   *.webp binary
   *.ico binary
   *.woff binary
   *.woff2 binary
   ```
   `eol=lf` overrides `core.autocrlf` per path, so the warning disappears and every checkout is LF on every machine.
2. Run once: `git add --renormalize . && git commit -m "chore: enforce LF line endings"`.
3. Add `.editorconfig` (`end_of_line = lf`, `insert_final_newline = true`, `charset = utf-8`, `indent_style = space`, `indent_size = 2`) and `"endOfLine": "lf"` in `.prettierrc` (Prettier's default, but explicit).
4. Optional: `git config core.autocrlf false` in this repo only. Do not change the system setting.

Do this as the first Phase 0 task, before the scaffold adds hundreds of files. Three of the plan's own scripts depend on it (see M9).

### C. Constants split into data constants and class constants

Recommendation: keep the per-component `constants.ts` for **data** (limits, defaults; already in the folder contract) and add a library-wide `shared/classes.ts` for **class constants** so every component's focus ring, disabled look, loading cursor and touch target come from one place. Use `.ts`, not `.tsx` (no JSX in a constants file). Compose them into the cva base rather than branching at runtime where an attribute already exists; where no attribute exists, set `data-disabled` and let the same constant apply. If explicit branching reads better: `cn(base, disabled && DISABLED, loading && LOADING, className)` — still constants, still one place. Hover/focus constants are necessarily variant-prefixed strings.

### E. Icons: keep `<Icon name="…">`, render inline SVG from one generated module per icon (Omar's decision, refined 2026-09-21)

Omar's requirement: the API stays `<Icon name="arrow-left" />`; the component lazy-loads internally so that a 20 000-icon set never loads everything; Omar's own proposal was "put the SVG path data in a constant instead of reading files". Honest assessment: the API is right and the instinct (inline SVG data, no file reads, no requests) is right; only the container is wrong. A **single hashmap** of every icon is imported by the library's client files (Select's chevron, Accordion's caret, Dialog's close button), so the whole map ships to the browser — 100 icons ≈ 30-40 KB gzip in every client bundle, 20k icons impossible. The plan's **sprite** fails the other way (one 8 MB file, one hash invalidating everything). The mechanism below keeps the API, keeps Omar's inline-SVG idea, and ships or loads exactly the icons that are used.

Proposed edit — replace sections 7.1-7.3 (lines 497-554) and D4 (line 93):

> **D4 | `<Icon name>` renders inline SVG from one generated module per icon | Only the icons that are used are loaded (server) or shipped (client); no requests, no files to serve, works in OG images; the set can be any size.**
>
> **7.1 Approach.** Every icon becomes one tiny ES module: `packages/icons/src/icons/arrow-left.ts` → `export const arrowLeft: IconData = { viewBox: '0 0 256 256', path: 'M…', directional: true }`. Nothing imports all of them at once. `<Icon name="arrow-left" />` renders the icon inline, `<svg viewBox …><path d="…" fill="currentColor" /></svg>`, so the HTML is complete on first paint, no network request is made, and the icon works wherever HTML works (Open Graph images, e-mail, RSS). A 20 000-icon set costs nothing until an icon is rendered.
> **7.2 Pipeline.** `pnpm icons:build` runs SVGO on every file in `raw/`, rewrites colours to `currentColor`, extracts `viewBox` and the merged path, and writes: one module per icon (`icons/<name>.ts`, LF), `names.generated.ts` (the `IconName` union), `directional.generated.ts` (patterns `arrow-*`, `caret-*`, `chevron-*` plus a manual list), and `loaders.generated.ts` — a map of **lazy loaders**, `{ 'arrow-left': () => import('./icons/arrow-left.js'), … }`, used only on the server. Each entry is a separate code-split chunk, so the map itself is a few bytes per icon and never pulls path data in until called.
> **7.3 The two entry points.**
> - **Server: `<Icon name>`** in `packages/react/src/components/icon/index.tsx` is an async Server Component: `const icon = await loadIcon(name)` (the loader map, with an in-memory cache), then `<svg width={size} height={size} viewBox={icon.viewBox} role={label ? 'img' : undefined} aria-label={label} aria-hidden={label ? undefined : true} focusable="false" className={cn('inline-block shrink-0', flip && 'rtl:-scale-x-100', className)} {...rest}><path d={icon.path} fill="currentColor" /></svg>`. `size` is a CSS length (default `1em`). Because it is async it can be rendered from any Server Component but never imported by a client file.
> - **Client and shared: `<Svg icon={…}>`** in `components/svg/index.tsx` (a shared component, no directive; exported as `@topclassui/react/svg`): the same markup, synchronous, taking an `IconData` object. Every library file that can end up in a client bundle — `client.tsx` files **and** shared components such as Button — imports the icon it needs explicitly (`import { spinner } from '@topclassui/icons/spinner'` → `<Svg icon={spinner} />`), so only that icon's ~300 bytes ship. `components/icon/index.tsx` starts with `import 'server-only'` so importing the async `<Icon>` from a client or shared file fails at build time instead of at runtime, and a lint rule forbids importing `loaders.generated` outside that file. Inside the library, `<Icon name>` therefore appears only in `index.tsx` files of Sp components that resolve data-driven names; app code uses `<Icon name>` in its Server Components and `<Svg icon>` in its client components.
> - **Names in data props** (`MenuItem.icon: IconName`, `TabItem.icon`, `Toast` tones): the server half of the component (`index.tsx`) resolves names to `<Icon name>` elements before passing items to `client.tsx`; the client contract carries `icon?: ReactNode`. This is the server/client split doing what it is for, and it keeps string names in the public API for the docs, the inspector and AI tools.
> **Sets.** The built-in set is `packages/icons/raw/` (the allow-list, ~100-300 icons). Apps register more sets (a brand set, a 20k library) with `topclassui-icons add-set <name> <dir>`, which generates the same modules, names and loaders under `<name>/` so `name="brand:facebook"` is type-checked too. Names are `set:name`; the built-in set needs no prefix.
> **Repeated icons.** A list of 200 rows each with a chevron inlines the path 200 times; gzip removes almost all of it (identical strings), and long lists are virtualised anyway (8.5). Measured in Phase 3; if a page ever needs it, a per-page `<symbol>`/`<use>` dedupe can be added behind the same API.
> **Icons page:** a virtualised grid (addition F) of every set, so 20 000 icons render as a few hundred DOM nodes; it is a collection (8.5) whose `loadMore` is a Server Action returning the next page of icon data, so the browser only ever holds the visible window.

Trade-offs stated plainly: no requests, no files to serve, no same-origin rule, no pop-in, works in OG images and e-mail; the costs are that the same icon repeated on one page repeats its path data in the HTML (gzip removes almost all of it; long lists are virtualised), and that client files must import icons explicitly by module rather than by string (a rule, enforced by lint, and the reason the whole set can never leak into a bundle). Compared with a single hashmap constant: same inline result, but tree-shakeable. This also removes the three sprite bugs listed in S4 (unscanned `rtl:` class → `<Icon>` and `<Svg>` live in `packages/react` and are scanned there; hand-joined classes → `cn()`; `--out` mismatch → no URLs exist).

Other plan lines that still say "sprite": line 71 → `Phosphor (default), inline SVG from one generated module per icon`; line 125 → `raw SVGs, build script, one module per icon, generated names/loaders, CLI`; line 1084 → `| Icons | each generated module under 600 bytes; a client bundle contains only the icons its components import |`; line 1365 → "`packages/icons` (section 7), the first 40-60 icons, the icons page, and the `topclassui-icons add-set` CLI"; line 1367 → replace "the sprite is cache-busted by hash" with "a client bundle that uses three icons contains exactly three icon modules (size-limit entry)". `@topclassui/icons` package.json: `exports` `.` (`IconName`, `IconData`, `DIRECTIONAL`, `loadIcon`), `./*` → `./dist/icons/*.js` (one icon each), `./package.json`; `sideEffects: false`; `bin: { "topclassui-icons": "./dist/cli.js" }`; `files: ["dist"]`; no React dependency. `@topclassui/react` gains `./svg` (shared `<Svg>`) next to `./icon` (server-only `<Icon>`) in its exports map (M1).

### F. Collections: a visible-rows knob, windowing, and page-by-page loading — for every list-like component (Omar's requirement, generalised)

Proposed edit — new section **8.5 The collection contract** (and references from 5.2, 6.2, 8.2, 10, 12, 18):

> **8.5 The collection contract.** Every component that renders a list of items — Select, MultiSelect, Combobox, Autocomplete, Command, Dropdown/ContextMenu/Menubar items, TagsInput suggestions, TreeView, Table, DataTable, VirtualList, LoadMore, Carousel, FileUpload file list, Timeline, the icons page grid, LayersPanel — shares one contract and one client hook, so behaviour is identical everywhere:
>
> ```ts
> // shared/contracts/collection.ts
> export interface CollectionProps<T> extends StateProps {
>   items: readonly T[]                     // the pages loaded so far, in order
>   getKey: (item: T) => string             // stable identity across pages
>   visibleRows?: number | undefined        // rows before scrolling; default from the --tc-list-rows knob
>   virtualize?: 'auto' | boolean | undefined // 'auto' (default): on when items.length > collection.virtualizeAbove
>   estimateRowHeight?: number | undefined  // px; default from the control size
>   hasMore?: boolean | undefined           // more pages exist on the server
>   loadMore?: (() => void | Promise<void>) | undefined // called once when the window reaches the threshold; client-only or Server Action
>   loadMoreThreshold?: number | undefined  // rows from the end that trigger loadMore; default 10
>   selectedItem?: T | undefined            // the selected value's item when it is not in the loaded pages (Select/Combobox)
> }
> ```
>
> - **Knob.** `--tc-list-rows: 7` in the tokens file (section 6.2) sets the default number of rows shown before a list scrolls, next to radius and density; `visibleRows` overrides it per instance by setting the variable inline (`style={{ '--tc-list-rows': n }}`, allowed by rule 5.2). Popups still clamp to Base UI's `--available-height`, so the knob is the maximum, not a fixed height. `<TopClassProvider collection={{ visibleRows, virtualizeAbove, pageSize, loadMoreThreshold }}>` sets app-wide defaults for client components. Precedence: `visibleRows` prop > provider `collection.visibleRows` > `--tc-list-rows`; server-rendered lists (Table, LoadMore) read only the CSS knob, because the provider is client-side.
> - **Windowing.** `shared/collection/use-collection.ts` (client) wraps TanStack Virtual (optional peer, loaded only by components that use it): it renders only the rows in view plus an overscan, recycles rows on scroll, measures variable heights, and exposes `scrollToKey`, `scrollToIndex`. Above `virtualizeAbove` (default 200) it is on automatically; below it, rows are plain DOM. Phase 4 acceptance: "the Select/Combobox virtualised demo follows Base UI's `@tanstack/react-virtual` example and a keyboard test proves `aria-activedescendant` tracks rows that are not mounted".
> - **Incremental loading.** When `hasMore` is true and the window reaches `loadMoreThreshold` rows from the end, the hook calls `loadMore()` once, sets `status: 'loading-more'` (a new value of the state contract, rendered as a trailing skeleton row), and does not call it again until `items` grows or `loadMore` rejects. The app owns the fetching, the cursor and the cache; the component only asks. `LoadMore` and paginated server lists keep a real `href` for the next page so crawlers and no-JS users reach every item.
> - **Edge cases every collection component must handle (and test):** 10 000 items with `virtualize: 'auto'` → fewer than 100 DOM rows at any time, 60 fps scroll, memory stable; `loadMore` that rejects → `status: 'error'` at the tail with a `Try again` row (`labels.retry`), the loaded rows stay; `loadMore` in flight while the user filters (Combobox) → the stale response is ignored by request id; `selectedItem` not present in loaded pages → the trigger shows its label from `selectedItem`, never blank; duplicate keys across pages → dev-time warning, second occurrence dropped; empty first page → `status: 'empty'`; keyboard: Home/End, PageUp/PageDown and type-ahead work over items that are not mounted (the hook scrolls first, then focuses); screen readers: `aria-setsize`/`aria-posinset` reflect the **total** when known, `aria-busy` while loading more; RTL horizontal lists (Carousel, scrollable Tabs) mirror scroll direction and `--tc-dir`; scroll position is preserved when pages are prepended or the list re-renders; very tall rows (Timeline) use measured heights, not estimates; the server-rendered first page (Table, LoadMore) is real HTML and hydrates without re-rendering.

### H. One scroll policy for every component (Omar: "tooltip, dropdown, etc. — all handled, scrolled, as possible")

The plan handles scrolling in two places (popups shrink to `--available-height` and scroll inside, 10.1; lists window and page, 8.5) but has no single policy, so Dialog, Drawer, Tooltip, sticky bars and mobile scroll chaining would each be decided ad hoc. > **10.5 Scrolling.** Every component follows these rules; `shared/classes.ts` exports the class constants (`POPUP_BOUNDS`, `SCROLL_Y`, `SCROLL_X`, `STICKY_EDGE`; values in Part 1b-C) so no component writes its own. The body scroll lock itself is Base UI's.

> 6. **ScrollArea** is the one component that draws custom scrollbars (Base UI ScrollArea; Tailwind 4.3 `scrollbar-*` utilities as fallback), used by Command, Sidebar, TableOfContents, the icons grid, DataTable; everything else uses native scrollbars. > 7. **Horizontal scrolling** (scrollable Tabs, Carousel, Toolbar overflow, wide Table): `SCROLL_X` with `scroll-snap-type: x mandatory` where items are discrete (Carousel, Tabs), keyboard arrows move the selection and scroll it into view, edge fades signal overflow (`mask-image`), the axis mirrors in RTL through `--tc-dir`, and wide Tables scroll inside a `Table.Scroll` wrapper with sticky first column (`start-0`, i.e. `inset-s-0`) and sticky header row.

> 9. **Windowed lists** (8.5): row recycling never resets the scroll position; prepending pages preserves the visual position; `scrollToIndex`/`scrollToKey` are the only programmatic scroll APIs and both accept `{ block: 'nearest' | 'center' | 'start' }`.
> 10. **Page-level:** the docs app sets `scroll-behavior: smooth` only under `prefers-reduced-motion: no-preference` (`--tc-motion`), restores scroll position on back navigation (Next.js default), and never uses `overflow: hidden` on `body` outside Base UI's scroll lock.

#### M2. `cn()` cannot make the consumer's `className` win for the knob utilities [docs: tailwind-merge 3.7.0 default config]
